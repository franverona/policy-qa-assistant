## Records

**2026-11-18 — TypeScript / Next.js for everything.** One language end to end, so the UI, API, ingestion and eval runner share types. Python has better PDF/ML tooling, but `unpdf` (pdf.js) gives per-page text, which is all citations need. Alternative: FastAPI + Next.js (two languages, two CIs).

**2026-11-18 — Tailwind CSS v4 for styling.** Quick to build the chat UI with, styles stay next to the markup, and there's no design system to maintain for a demo. Alternatives: CSS modules (more files, slower to iterate) or a component library (more weight than a few screens need).

**2026-11-18 — Postgres + pgvector for both search modes.** Full-text (`tsvector`, GIN) and vector (HNSW cosine) live in one table, so hybrid search is one database and one transaction. Alternatives: a dedicated vector DB plus Elasticsearch (more moving parts, nothing gained at this scale).

**2026-11-18 — Local models through Ollama by default.** No API costs, and the data never leaves the machine (a selling point for an insurer). Chat `qwen3:8b`, embeddings `nomic-embed-text` (768-d), rerank `bge-reranker-base` via transformers.js, sized for an M1 Pro with 16 GB. All model names are env vars. `LLM_PROVIDER=anthropic` is optional and only for chat; Anthropic has no embeddings API, so embeddings always use Ollama.

**2026-11-18 — Clause-aware chunking with heading paths.** Chunks follow numbered clauses (~350 tokens, split only when a clause is long, ~15% overlap), and each one is prefixed with `Document › Section › Clause`. Clauses are the unit agents cite. The prefix lets BM25 and embeddings tell apart near-identical clauses from different products and years. Alternative: fixed-size windows (simpler, but they cut clauses in half and lose which policy a chunk belongs to).

**2026-11-18 — Hybrid search with RRF, then a cross-encoder.** Full-text catches exact policy codes and clause numbers. Vectors catch paraphrases. Reciprocal Rank Fusion (k=60) merges ranks without normalising scores. A cross-encoder reranks the top 20 to 5, because it reads the query and the chunk together.

**2026-11-18 — Three "I don't know" gates.** (1) A rerank score below a threshold returns IDK before the LLM is called. (2) The LLM can return `answerable: false`. (3) Every citation must point to a retrieved chunk, and an answer with no valid citations becomes IDK. A wrong answer is a compliance risk, so the system prefers to abstain.

**2026-11-18 — Evals run locally, CI uses fixtures.** CI never calls a model. It runs the eval runner and scoring against recorded responses as a smoke test. Real evals run locally with `pnpm eval`, and each report records the models that produced it.

**2026-11-18 — No streaming at first.** Structured JSON answers are easier to validate whole. shortcut: revisit if latency hurts the demo.

**2026-11-18 — Config: no defaults in code, checked at server start.** Every value, model names included, comes from `.env`, with `.env.example` as the single place that holds defaults. `src/config.ts` (zod) runs from `instrumentation.ts`, so a missing variable stops the server with a list of what's missing, instead of failing on the first request. It's lazy, so `next build` works in CI without an env file. Alternative: defaults in code (fewer variables to set, but two sources of truth and silent fallbacks).

**2026-11-18 — Pre-commit only formats and scans for secrets.** lint-staged runs Prettier on staged files, then `gitleaks git --pre-commit --staged`. Lint, type-check and tests run in CI, which keeps commits fast. GitHub secret scanning and push protection are a second line of defence, because the repo is public.

**2026-11-18 — Code style copied from blitzr.** Same Prettier config (no semicolons, single quotes, 100 columns, `prettier-plugin-tailwindcss` sorts classes) and the same ESLint presets (Next core-web-vitals + TypeScript, `eslint-config-prettier` last), so Fran's repos read the same. CI runs `pnpm format:check`, which also catches commits that skipped the hook. The PR-title check (commitlint in CI) is copied too, limited to `feat|fix|chore|docs|test`. Squash merges use the PR title as the commit message, so this keeps main's history conventional without a commit-message hook. Left out: `eslint --fix` in lint-staged (the hook here only formats) and blitzr's lockfile-pinned commitlint install (it exists for Dependabot's cooldown; this repo has no Dependabot, and `--frozen-lockfile` already pins).

**2026-11-18 — Failing CI blocks merges.** A repository ruleset on main requires the `check` and `commitlint` jobs (from GitHub Actions) to pass. It doesn't require the branch to be up to date with main: PRs are small and sequential, so the extra rebase step isn't worth it. A ruleset, not classic branch protection, because rulesets are the current API and are visible under Settings → Rules.

**2026-11-19 — CI runs against a real Postgres.** The `check` job has a `pgvector/pgvector:pg17` service container and sets `DATABASE_URL`. Database tests use `describe.skipIf(!DATABASE_URL)`, so `pnpm test` still passes on a machine without the db running (vitest doesn't load `.env`). Replaces the earlier "CI without Postgres" note.

**2026-11-19 — Two tables, citations enforced by the schema.** `documents` mirrors the corpus frontmatter plus `path` (the rendered file) and `content_hash` (so ingest can skip unchanged docs). `chunks` holds `heading_path`, `page` (PDFs) or `anchor` (wiki), `content`, `embedding` and a generated `tsv`. A check constraint rejects a chunk with neither `page` nor `anchor`, so every stored chunk can be cited. `tsv` is `to_tsvector('english', heading_path || ' ' || content)`, generated so ingest can't forget it, and it includes the heading path so clause titles and policy names are searchable. Vectors use HNSW with `vector_cosine_ops` (no training step, unlike IVFFlat, and fine on an empty table). Re-ingesting a doc deletes it (chunks cascade) and inserts it again in one transaction.

**2026-11-19 — `vector(768)` is hard-coded in SQL.** HNSW needs a fixed dimension, and a plain `.sql` migration can't read `EMBED_DIM`. A different embedding model (e.g. `bge-m3`, 1024-d) gets its own migration and a re-ingest, and `m1-ingest` will check that `EMBED_DIM` matches the column. Alternative: a `{{EMBED_DIM}}` placeholder, but a migration that has already run never picks up a change, so it would only hide the mismatch.

**2026-11-19 — Migrations: ~20 lines, no library.** `pnpm db:migrate` applies `db/migrations/*.sql` in name order, one transaction per file, and records each one in `schema_migrations`. It reads only `DATABASE_URL`, so it doesn't need the model variables. Alternatives: node-pg-migrate or dbmate (down migrations and locking aren't needed for a single-developer demo).

**2026-11-19 — No LLM framework: plain `fetch` to Ollama.** `src/llm/` is two endpoints (`/api/chat`, `/api/embed`) in about 100 lines, and every request is visible, which makes the fixture keys and debugging straightforward. Weighed: the Vercel AI SDK (`ai` 7, the strongest option: `generateObject`, `embedMany` and an Anthropic provider, but four majors in two years, a community-maintained Ollama provider (one option adds `jsonrepair`, which would hide broken JSON), and we'd still hand-write the prefixes, `think` and fixtures); LangChain.js / LlamaIndex.TS (they bring loaders, splitters and retrievers, which are exactly the parts this project builds and evaluates itself); the official `ollama` client (saves about 20 lines). Revisit the AI SDK if we need streaming, tool calling or several hosted providers. The M5 Anthropic provider is one more `fetch`.

**2026-11-19 — `chat()` always returns schema-validated JSON.** It takes a zod schema, sends it to Ollama as `format` (JSON-schema-constrained decoding), and parses the reply with the same schema, so callers get typed data or an error, never prose to regex. Options are `temperature: 0` (repeatable answers for evals) and `think: false` (qwen3 otherwise writes a long reasoning trace first: slower, and the citation pipeline never reads it). Both are candidates for M6 tuning. `usage` (input/output tokens) is returned now so M5 logging doesn't change the signature.

**2026-11-19 — Embedding task prefixes come from config.** `nomic-embed-text` was trained with `search_query: ` / `search_document: ` prefixes, and embedding without them hurts retrieval. `embed(texts, kind)` adds `EMBED_QUERY_PREFIX` or `EMBED_DOC_PREFIX`: required env vars, empty for models without prefixes (e.g. `bge-m3`), following "no defaults in code". `embed` also checks every vector is `EMBED_DIM` long, so a model/column mismatch fails at the first call.

**2026-11-19 — Fixtures: `LLM_PROVIDER=record` / `fixture`.** `record` calls Ollama and saves each exchange to `fixtures/llm/<op>-<hash12>.json` (`model`, `request`, the raw `response`, `recordedAt`). `fixture` replays them and never calls a model, and a missing fixture throws with the key and the hint to re-run with `record`. The key is a sha256 of the request **without the model name**, so changing `CHAT_MODEL` doesn't break CI (the file still says which model produced it). Replays go through the same parsing as live calls. Recording is a provider rather than a wrapper script, so any flow records exactly the requests the real code makes (e.g. `LLM_PROVIDER=record pnpm eval`). `pnpm llm:smoke` (one chat, one embed of each kind) checks the Ollama setup, and its recorded fixtures are replayed in CI, so tests parse real Ollama responses, not just mocks. Fixtures are excluded from Prettier because they're generated.

**2026-11-19 — PDFs parsed with unpdf, headings found by font size.** `parsePdf` reads each page's text items (pdf.js via `unpdf`) and never looks at the Markdown source, as it would have to with real policy PDFs. The most common font size is body text; larger sizes, largest first, are heading levels; smaller text (the "Policy form · Effective" line) is skipped because `documents` already stores it. A vertical gap over 1.5 lines starts a paragraph, and each paragraph keeps the page it starts on, so a chunk that begins mid-clause on the next page cites that page. Lines that wrap after a compound-word hyphen ("non-" / "payment") join without a space. A test parses all 30 rendered docs back and checks headings and text against their sources. Alternatives: hard-coding our renderer's sizes (breaks on any other PDF) or tagged-PDF structure (most real PDFs aren't tagged).

**2026-11-19 — Wiki HTML parsed with a regex, chunks sized by chars ÷ 4.** `parseHtml` matches `<h1–3 id>`, `<p>` and `<li>` from our own renderer. shortcut: swap for `node-html-parser` or parse5 when real wiki exports arrive. The chunker makes one chunk per clause (or per section's text before its first clause), and only splits past ~350 tokens, at paragraphs and then sentences, carrying up to 15% as trailing sentences into the next piece. No clause in the current corpus is that long (the longest is ~130 tokens), so splitting only runs in tests. Tokens are estimated as characters ÷ 4 instead of loading a tokenizer. `content` has no heading prefix: the `tsv` column adds `heading_path` itself, and ingest prepends it before embedding.

**2026-11-19 — Ingest: hash-skip per doc, embed outside the transaction.** `pnpm ingest` reads metadata from the source frontmatter (our document catalog) and text only from the rendered PDF/HTML. `content_hash` is sha256 of source + rendered bytes + `EMBED_MODEL`, so an unchanged doc is skipped (a re-run takes ~0.3 s) and switching embedding models re-embeds everything. Parser or chunker changes don't change the hash: run `pnpm ingest --force`. Each changed doc is embedded first (one batched `/api/embed` call, `heading_path` prepended), then replaced in one transaction, so an Ollama failure leaves the previous version intact. Docs missing from `corpus/sources` are deleted. Ingest checks `chunks.embedding` is `vector(EMBED_DIM)` before doing anything. `embed` is passed in, so the test uses a fake embedder in its own `ingest_test` schema and never touches the dev data. `migrate()` takes an advisory lock per file, so parallel test files can't race on `create extension`. First ingest: 30 docs, 339 chunks, ~8 s on an M1 Pro.

**2026-11-20 — Full-text search: `websearch_to_tsquery` with OR, ranked by `ts_rank_cd`.** `fullTextSearch(sql, query, limit)` matches `chunks.tsv`. `websearch_to_tsquery` ANDs every word, so a full question ("does homeshield cover sump pump overflow") only matches chunks containing all of its words and usually finds nothing. We rewrite `&` to `|` in the generated query and keep `& !` (`-negation`) and quoted phrases (`<->`). `ts_rank_cd` (cover density) ranks chunks that match more words, closer together, first. No length normalisation, since chunks are already similar in size. Ties are broken by chunk id. The candidate count is the caller's `limit` (RRF decides it, and it's an M6 knob). OR casts a wide net and lets weak matches in ("cover" matches every definition of "covered"), which is fine because RRF and the reranker sort that out. Alternative: AND with an OR fallback when nothing matches (two queries, and its results are harder to explain). Gap found: policy codes are only in the PDF's skipped "Policy form" line, so a code search misses the policy itself; that's fixed in `m2-policy-codes`.

**2026-11-23 — Policy codes prefix every chunk's heading path.** Ingest writes `HM-END-04 · Water Backup… › Section › Clause` for docs with a `code`, so the generated `tsv` and the embedding text (both built from `heading_path`) contain the code, and citations show it. `·`, not `›`, because the code isn't a heading level. Postgres splits `HM-END-04` into `hm-end`, `hm`, `end`, `04`, and `websearch_to_tsquery` makes that a phrase, so `HM-END-04` doesn't match `HM-PA-END-04`. Every hit contains the exact code, but a clause that cites a code (e.g. the auto policy citing `HM-PA-END-06`) can outrank the endorsement itself. RRF and the reranker deal with that. Alternatives: stop skipping the "Policy form" line in `parsePdf` (puts the code in only the first chunk and adds metadata noise to the content), or add a `documents.code` term to `tsv` (a migration, and the code still wouldn't be embedded). The content hash doesn't change, so existing databases need `pnpm ingest --force`. No eval scores yet (the runner arrives in M4).

**2026-11-19 — No app container yet.** `make dev` runs Postgres in Docker and Next on the host (fast reloads; Ollama is on the host anyway), and now also checks Ollama, pulls the chat/embed models and ingests. A production Dockerfile + `app` compose service moves to M7, where the README's "how to run" needs a one-command start.

**2026-11-18 — Corpus is written as Markdown and rendered to PDF/HTML.** Each doc in `corpus/sources/` is a small Markdown subset (`#` title, `##` section, `###` clause, `-` bullets, paragraphs) with `key: value` frontmatter (`id`, `title`, `type: policy | wiki`, optional `code`, `effective`). `pnpm corpus:render` turns policies into PDFs with pdfkit and wiki pages into HTML with an `id` on every heading, so citations can point to `#page=N` or `#anchor`. The rendered files are committed, so ingestion and CI never need the renderer. Built-in fonts and fixed PDF dates keep the output byte-identical, which makes re-renders show up as real diffs. Pages break wherever the text runs out, so some clauses cross pages, just like real PDFs, but a heading always stays on the same page as its first lines, so the page a clause starts on is the page with its first text. Alternatives: hand-made PDFs (can't be reviewed or diffed), or HTML-to-PDF with a headless browser (a much heavier dependency for the same result).
